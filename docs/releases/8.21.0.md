# Forge 8.21.0

Forge 8.21.0 adds a transport-neutral Chain API with verified audited clients,
an Experimental authenticated ordered-state library and the database boundaries
needed to host them. It also fixes HTTP cancellation and response-write deadline
ownership for long-poll and streaming handlers.

The authenticated proof schema and persisted format are not production-stable.
They remain behind the independent security review gate described below. The DB
Store and DB Object source APIs remain Preview.

## Chain API

The new `forge_chain_api` target owns the `forge::chain::api` contracts for:

- chain info, block, state and transaction queries;
- transaction submission as a separate authority from ordinary reads;
- producer administration as a separately resolved trusted surface;
- HTTP and P2P-capable raw clients;
- verified clients that validate chain identity, finality, authenticated point,
  range and change proofs, and product-provided projections;
- bounded local ABI JSON/binary conversion.

Wire records live in the flat `forge.chain.protocol.audit`, `info`,
`block_query`, `state_query`, `transaction_query` and `admin` modules. Runtime
interfaces and clients live in direct `forge.chain.api.*` modules. There is no
aggregate `forge.chain.api` module and no RPC compatibility facade.

`raw_client` contains ordinary read handles only. Products resolve
`submission_client` where transaction admission is authorized and resolve
`admin` only in trusted operational processes. Submission acknowledgements do
not claim inclusion or finality; consumers use the verified transaction status
or await methods for those guarantees.

Audited clients enforce local request, response, item-count, proof and decoded
allocation limits independently of peer-advertised capabilities. Finality
checkpoints are caller-installed trust, not server assertions. A typed
projection verifier must recompute composite public responses from the exact
authenticated source bytes; missing projection support fails closed.

## Authenticated State: Experimental

The new `forge_db_authenticated` target provides immutable path-copied AVL
state, content-addressed values, retained version roots, point proofs, ranked
forward/reverse range proofs, change proofs, pruning and garbage collection over
a DB Core driver. It can join the same DB Core transaction as DB Object and DB
Revision so a projected state root commits or rolls back with the source data.

The C++ API, proof schema and persisted node/root format are **Experimental**.
Schema v3 uses SHA-256 domain and length framing and persisted format version 4.
It is intentionally incompatible with all earlier experimental authenticated
formats. Forge provides no compatibility reader or legacy mode: a pre-8.21
experimental authenticated store must be reset or explicitly migrated before
it is opened with this release.

Release packaging does not make authenticated state production-ready. A
consumer must not activate its state root in a production genesis until an
independent cryptographic and implementation review has accepted the exact
Forge commit, proof schema, persisted format, threat model and remediation
status. See the
[authenticated state production gate](../security/authenticated-state-production-gate.md).

Forge does not claim that schema v3 is Cosmos ICS23-compatible and does not
relabel native proofs as ICS23.

## DB Store Preview

The Preview DB Store surface now supports:

- additional physical DB Core families through `store_config::families`;
- `store_handle::authenticated(config)` over a named store's private driver;
- backend-owned durable checkpoints through `store_handle::create_checkpoint`;
- `monotonic` or opt-in `transactional` DB Object ID allocation.

`transactional` ID allocation requires the single-writer policy and makes
sequence records participate in savepoint rollback and DB Revision. The default
remains `monotonic`, where rollback may leave intentional gaps.

DB Store's Preview aggregate shapes changed. `object_layer_config` adds
`id_allocation`; `store_config` and `store_status` add `families`. Code that uses
positional aggregate initialization must insert those fields or move to
designated initialization. Config files may omit both new settings and retain
the existing defaults. No compatibility aliases or legacy status shapes are
provided.

The DB Object header remains persisted format version 1, and this release does
not change existing DB Object, Blob or Revision record layouts. An 8.20 store
that keeps its current layers and default ID policy requires no reset, replay or
data migration. A newly enabled authenticated family starts empty. Any family
containing data from an earlier Experimental authenticated format follows the
explicit reset-or-migrate rule above. Ranked-index schema changes on populated
storage also continue to require an explicit product migration or rebuild;
Forge does not perform a hidden startup scan.

## C++ Source Migrations

### Transaction Submission Deadlines

`forge::chain::protocol::transaction_submit_request` appends
`std::uint64_t timeout_ms = 30'000`. The field is part of the described JSON
shape and the canonical raw record after `retry_blocks`. Producers must append
the unsigned 64-bit value; generated JSON clients must send `timeout_ms`.
Payloads in the old shorter shape are malformed in 8.21 and are not accepted by
a legacy reader.

Batch submission now takes
`forge::chain::protocol::transaction_submit_batch_request` instead of
`std::vector<transaction_submit_request>`. Migrate calls to
`submit_batch({.transactions = std::move(transactions), .timeout_ms = 30'000})`.
The HTTP body likewise changes from a top-level array to an object containing
`transactions` and `timeout_ms`; regenerate clients from the 8.21 schema.
Calls to the removed `require_transaction_batch_within_limits(vector, limits)`
helper migrate to `require_request_within_limits(batch_request, limits)`.

Both submission HTTP routes derive their transport timeout from the request
deadline plus five seconds of grace. Zero deadlines are invalid and values over
`service_limits::max_await_ms` are rejected. The batch deadline bounds the whole
call: each item is additionally bounded by its own deadline and the remaining
batch budget, never by an unbounded sum. No compatibility alias or legacy wire
reader is provided.

### Protocol Time JSON

`forge::chain::protocol::time_point` JSON now preserves every nonzero fractional
microsecond instead of silently truncating it. Whole-second values retain the
existing 19-character `YYYY-MM-DDTHH:MM:SS` spelling. Fractional values use
`.mmm` when exactly millisecond-aligned and `.ffffff` otherwise; readers accept
one through six fractional digits. Regenerate any golden JSON that previously
depended on the lossy whole-second output for a fractional value.

### API Method Descriptors

`forge::api::core::method_descriptor` inserts `response_traits` immediately
after `response_type`. It also inserts `request_encoder`, `response_encoder`,
`request_decoder`, `response_decoder`, `request_validator` and
`response_validator` after `errors` and before the four raw invoker fields.

This changes the meaning of positional aggregate initialization. Prefer
`FORGE_API` or `forge::api::core::contract_builder`, which populate the codec
and validation callbacks. A direct positional initializer must insert one value
for `response_traits` after `response_type` and six callback values after
`errors`, before `raw_invoker`. Use `{}` for each unused inserted field, or move
the initializer to designated members. Do not append the placeholders after the
raw invokers.

### P2P Resolver Deadlines

`forge::plugins::p2p::resolver::config` inserts `request_deadline_ms` after
`open_deadline_ms` and before `max_cached_peers`. A positional initializer must
insert `0` at that position, or name the members with designated initialization.
The serialized setting is `request-deadline-ms`; omitting it retains the zero
default and preserves method-owned deadlines.

`forge::plugins::p2p::resolver::resolve_options` likewise inserts
`request_deadline` after `open_deadline` and before `force_refresh`. Migrate
`resolve_options{query, open, force_refresh}` to
`resolve_options{query, open, std::chrono::milliseconds{0}, force_refresh}`, or
use designated members. A non-zero value adds a connection-wide request
deadline; zero leaves deadline ownership with the method.

### DB Store Driver Encapsulation

`forge::plugins::db::store::store_handle_state::require_driver()` is now a
private implementation hook. Consumer calls through `store_handle_state` no
longer compile, and there is no replacement public raw-driver accessor. Use
`store_handle::objects()`, `blobs()`, `revisions()` or `authenticated(config)`
for layer operations; use `begin_transaction()`, `begin_read()` and
`create_checkpoint()` for whole-store operations.

## HTTP Cancellation And Deadlines

HTTP client cancellation now reaches the operation that owns the active request
and releases the serialized per-connection queue. Timeouts remain typed gateway
timeouts and cancel the owner rather than degrading into generic availability
errors.

Generated HTTP API clients reconnect and retry one request after a stale
keep-alive close only for idempotent `GET`, `HEAD`, `PUT`, `DELETE` and
`OPTIONS` methods. `POST` and `PATCH` are never replayed after an uncertain
transport acknowledgement; transaction callers recover by transaction ID.

The server refreshes the socket write deadline before a buffered response,
stream header, each stream chunk and the final stream write. A route handler or
body producer may therefore wait longer than `idle_timeout` and still write its
response. `idle_timeout` continues to bound socket read/write operations and
keep-alive gaps; long-poll, streaming and Server-Sent Events owners must provide
their own application deadline, disconnect cancellation, concurrency and
backpressure policy.

While the runtime is running, `server::async_stop()` and synchronous
`server::stop()` calls from outside a runtime worker now complete only after the
accept loop and every active session loop have terminated. A runtime-worker
`stop()` schedules the same drain and returns to avoid self-deadlock. Once
shutdown begins, a session cannot dispatch another request, including when
cancellation arrives while a route handler owns the connection. Cleanup after
an already-stopped runtime remains non-waiting.

For Chain API long polling, an application deadline is restored as the declared
`forge::chain::api::exceptions::deadline_exceeded` error and maps to HTTP 504.
It is not rewritten as HTTP 503 transport unavailability.

## Debug Build Policy

A parent `Debug` configuration keeps Forge-owned targets on the normal Debug
profile, but compiles the vendored `secp256k1`, BN256, BLS12-381, SoftFloat and
MDBX implementation targets with target-local `-O2` (or `/O2` on MSVC). This
avoids production-scale cryptographic and deterministic-compute code running at
`-O0` while preserving parent sanitizer options and all Forge integration and
golden tests. No vendored source is modified by this policy.

## Package Components And Migration

Installed consumers request the new leaf components and link their exact
targets:

```cmake
find_package(Forge CONFIG REQUIRED COMPONENTS chain_api db_authenticated)

target_link_libraries(product PRIVATE
   Forge::forge_chain_api
   Forge::forge_db_authenticated
)
```

`chain_api` resolves its declared API, protocol, crypto, authenticated DB and
HTTP dependencies. Existing `plugins_db_store` consumers keep the same component
and target names; that component now resolves `db_authenticated` transitively.
Consumers should not depend on undeclared build-tree targets or invent aliases.

All C++ consumers of changed public aggregates or DB Store handles must rebuild
and apply the mechanical updates above. Existing Chain Protocol consumers may
import the new query modules directly; there is no removed Chain API predecessor
and no compatibility alias to add.
